1. Executive summary

The application's documentation is broadly sound but has drifted at the edges: the boundaries where a file was renamed, a tree was deleted, or a feature shipped and its planning document stayed behind. Sixteen places were found where a reader — including an AI agent that loads these files on every request — is sent to something that no longer exists.

16findings, all documentation
14approved for correction
0code, package or database changes

Overall health

Most of the 74 prose documents resolve cleanly. The problems concentrate in three habits rather than spreading evenly: a document that names a file by a path that was later reorganised; a planning document that was never retired once its feature shipped; and a diagram index that still advertises workflows the application no longer contains.

The highest-value items

  1. Always-applied guidance points at a deleted tree. The Spec Kit instruction file tells the agent that WeekendProject/ is the authority for checklists and the seed for the first feature. That folder is gone, so the instruction cannot be followed. It also names a helper script, drift.py, that the installed tooling does not contain.
  2. A living specification has six dead references. The drift ledger — a document meant to be kept current — cites five files that do not exist and one spec path that moved.
  3. The diagrams index advertises four workflows that are not there. The README describes five workflows and ten PDFs; only the startup-launch pair exists. Eight links resolve to nothing.
  4. A shipped feature still reads as unbuilt. The startup design brief says "nothing here is implemented yet" and points at a checklist that does not exist, although the feature has shipped.

Security and privacy

No vulnerability, credential or dependency issue was researched. One finding is privacy-adjacent: two documents link to file:///C:/Users/jkoll/… paths, which disclose a second workstation's profile name inside this repository. Removing them is approved.

What this changes for the people who use the application

Nothing at run time. Every approved change is an edit to a document or an instruction file. The benefit is to the people and agents who maintain the application: they stop following dead ends, and the review of a future change is not slowed by having to work out which document is still true.

4. Finding detail

DEV-001 · Guidance points at a deleted tree

The Spec Kit instruction file is applied to every request. Line 61 tells the agent that WeekendProject/PromptFiles/* remains authoritative for checklists, and line 64 names WeekendProject/Module_Mock/Spec.md as the seed for the first feature. Neither exists: the folder was deleted with the Module_Mock workstream, and the work survives as the first feature spec. Approved: point at specs/001-module-mock-visual-fallback/ and at the two checklist skills that already hold the rule.

DEV-002 · A helper script that is not installed

Line 45 explains why the Companion's Python helpers must be called with python rather than python3 — a real and current caution. It lists write-context.py, doctor.py and drift.py; the extension ships 17 scripts, and there is no drift.py. Approved: name doctor.py and keep the caution intact.

DEV-003 · A living document with dead references

The drift ledger is one of three living specs — documents expected to stay true. It cites FEATURES.md, OPEN-TASKS.md, RELEASE-NOTES.md, DeveloperUI-VisualPrompts.md, VALIDATION-PROMPT-SERVER.md and drift.py, none of which exist, and specs/001/tasks.md, which is now specs/001-module-mock-visual-fallback/tasks.md. Approved: repoint the spec path and remove the five dead references, saying in the line that those artefacts are gone.

DEV-004 · Diagrams for workflows that no longer exist

The diagrams README opens "Five workflows in this application" and presents a table of ten documents. The folder contains one workflow: pdf/startup-launch/ with an engineer and a plain language PDF, and five Graphviz sources for it. The other four workflows — work-order and generic-request request and setup flows — have neither a PDF nor a source. The refactor notes repeat the same eight dead links in a flat form. Approved: reduce the README to the workflow that exists and state plainly that the other four were removed with their flows; strip the dead links from the notes.

One check before implementing: confirm whether the four workflows were removed or only paused. The README's wording must match the answer, and "removed" is wrong if the diagrams are waiting to be rebuilt.

DEV-005 · A shipped feature that still reads as unbuilt

docs/startup/startup-rebuild-design-brief.md begins "Nothing here is implemented yet; the removal checklist is the first work" and defers its section references to STARTUP-REBUILD-CHECKLIST.md, which does not exist. The startup rebuild shipped as feature 010, and 27 of the brief's file references have since moved or been deleted. Approved: move the brief beside its feature, into specs/010-startup-rebuild/, where a planning document is read as a record rather than as current state.

DEV-006 · Proposals that cannot show their own pictures

Five design proposals render BEFORE and AFTER images. Each links them as siblings (name-the-authority-before.png), but the files sit in a pngs/ folder beside the proposal. The picture exists and the link is wrong, which is the cheapest kind of drift to fix and the most confusing to read.

5. Live guidance: instructions an agent follows

6. What stays as it is

Two findings were deliberately left alone, and the decision records that they must not be "tidied" later. Twelve defect records and one research record cite paths as they stood when they were written. A defect record is the evidence for a diagnosis; rewriting its paths would misrepresent where the fault was found, and a research record is a snapshot of what was known before the design. Both were reviewed and both are correct as history.

The same reasoning protects several things this audit noticed but did not raise: documents that name a deleted file while saying it was deleted, and the design proposals that share one template heading. Neither is drift.

10. Final recommendations

  1. Do Phase 1 first and on its own. Correcting the six live-guidance references is small, reversible and removes the only findings that cost every request rather than every reader.
  2. Answer the diagram question before Phase 3. "Removed" and "paused" lead to different sentences, and the wrong one would be a new inaccuracy in place of an old one.
  3. Treat the move of the startup brief as a record, not a rewrite. Its value is the design rationale; its paths are history.
  4. Keep a reference scan in the loop. This audit found 16 items with a mechanical scan plus a reading of each candidate. Re-running the same scan after any documentation change is the cheapest way to stop the same drift returning.
