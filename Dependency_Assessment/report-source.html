What this report is. A read-only assessment. It describes what was found, what was approved, and what the work would involve. It is not a record of work performed: no package was updated, no server installed, and no project, source or configuration file was edited. The companion specification, DEPENDENCY_AND_MODERNIZATION_SPECIFICATION.md, is the implementation input.

1. Executive summary

The application itself is healthy. What is unhealthy is the set of instructions and tools wrapped around it: the repository tells an AI assistant things that stopped being true, points it at a file that no longer exists, and registers two tool servers that cannot do their job. The cost is paid on every single request, before any work starts.

≈25,000tokens of instructions loaded before the first request is read
5verified wrong facts in the two always-loaded instruction files
54tool definitions from servers that cannot deliver their service

Overall health

Seventeen projects, one target framework, no continuous integration, and a documentation and instruction surface that has grown to roughly 90 KB of text that loads on every request. The application code was not in scope; the assessment covers the AI-facing configuration around it.

Update status

No package update is proposed. This was an AI-tooling audit, and the two servers involved are registration problems rather than version problems: the XAML inspection server is installed and up to date but has nothing to connect to, and the CSV server is at its only published version.

Security concerns

None of the approved work fixes a vulnerability, because no vulnerability was in scope. The two server removals reduce exposed surface: one is a local executable that can never serve a request, the other accepts a folder path and can write files. No secret value is reproduced in this report.

Modernization

The pattern is duplication rather than obsolescence. The same rules are written in two always-loaded files. The same commands exist as extension source, as agents and as skills. The single largest instruction file — a 27 KB UI-automation procedure — matches almost every code edit in the repository, whether or not the task involves UI automation.

AI development environment

Two servers registered, neither usable. Seventeen agent files that no tool can load, twelve of them pointing at extensions that are not installed. Twenty-four skill folders that no extension registers. These are recoverable in a day, and every change is a text edit.

Highest-value recommendations

  1. Load the UI-automation procedure on demand (AI-010). Removes about 27 KB from every code edit — the largest single saving available.
  2. Remove both MCP servers (AI-001, AI-004). Ends 54 tool definitions per request that cannot return anything useful.
  3. Correct the five wrong facts (AI-006) and the broken note pointer (AI-005). Wrong project counts and versions actively mislead.
  4. De-duplicate the instruction files (AI-008, AI-009, AI-012). About 6 KB of text is currently paid twice.

3. Per-component assessment

Each entry gives the current state, the evidence, why it matters to someone using the application, the risk of changing it, and the effort. Evidence is a command result or a file measurement taken on 26 November 2026.

XamlMcp — a tool server with nothing to connect to

Current stateRegistered in .mcp.json with every tool enabled. The tool itself is installed and passes its own health check (runtime .NET 10.0.15, server 1.0.0-preview.3).
EvidenceThe health check reports 0 instrumented desktop applications running and no discovery folder. A text search for the agent across every .cs, .csproj and .xaml file outside build output returns 0 matches.
Why it mattersThe server exists to inspect a running window. Without the in-application agent there is no window to inspect, so every request carries roughly 15 tool definitions that can only fail, and the instructions describe a ten-step workflow that cannot start.
SecurityRemoving it reduces the number of local executables the assistant can launch.
RiskLow. Restoring it is one configuration block, and should happen in the same change that adds the agent to the application.
EffortSmall — two edits, one configuration and one instruction section.
DecisionApproved — AI-001 and AI-002

CSV server — healthy, but its central operation fails

Current stateRegistered twice: once at the repository root pointing at docs/database (5,866 schema exports), and once under .vscode pointing at a folder that does not exist. It exposes 39 tools.
EvidenceThe server reports healthy, but loading a real schema file fails every time with a validation error in its own progress reporting (total … input_value='Validating file...'). The package has exactly one published release, from 13 August 2025, so there is no fixed version to move to.
Why it mattersThe repository reads these exports with ordinary PowerShell today. The server adds 39 tool definitions and a failing route, and the instructions tell the assistant to use it first.
SecurityRemoving it removes a server that accepts a storage path and can write files.
RiskMedium. Convenient in-session table analysis is lost. Mitigated by naming the PowerShell equivalent in the replacement instruction.
EffortSmall.
DecisionApproved — AI-003 and AI-004

Project instruction files — the largest recurring cost

Current stateTwo project instruction files, both loaded on every request: .github/copilot-instructions.md at 30,536 bytes and AGENTS.md at 4,735 bytes. Four further instruction files load on every request regardless of the task.
EvidenceSum of the six always-applied repository files is 57,337 bytes; six user-level files add 33,550 bytes. Total 90,887 bytes ≈ 25,000 tokens before a single file is read. Six rules appear in both project files: two build-failure signatures, the command-naming trap, the stored-procedure rule, the no-demo-mode rule and the view-model convention.
Why it mattersThis text is paid on every request, and it competes for attention with the task. Duplicated rules also drift: the two files already disagree on the SDK version.
RiskLow to medium. Deletions are reversible, but one deletion removes a workflow description the assistant may have been following; the report names it explicitly for that reason.
EffortSmall to medium — five proposals touch the same file, so the order matters.
DecisionApproved — AI-002, AI-005, AI-006, AI-008, AI-009, AI-012

UI-automation instruction — the largest per-edit cost

Current stateA 27,256-byte, 351-line procedure for driving the application's window, with a file-pattern match covering every XAML, C#, PowerShell and resource file in the repository.
EvidenceIt is the largest instruction file (24% of all repository instruction bytes) and its match pattern covers nearly every edit made in this codebase.
Why it mattersA change to a database helper pays for the whole UI-automation procedure. Microsoft's own guidance puts multi-step procedures in skills and conventions in instruction files.
RiskMedium. The skill must be discoverable from the task wording. Mitigated by keeping a short routing instruction that names it.
EffortMedium — one file split into two, plus one routing line.
DecisionApproved — AI-010

Agents, skills and instruction accuracy

Current state109 agent files (92 valid), 43 skill folders, 61 prompt shims, 13 memory notes. Instruction text states fifteen projects, fifteen audit tests and SDK 2.3.1; the build says seventeen, seventeen and 2.4.0. It also states that the Python launcher is broken; on this workstation it answers normally.
EvidenceTwelve agent files contain a single relative path and nothing else; all twelve targets resolve to files that are not installed. Five further agent files carry no header at all. Twenty-four skill folders duplicate commands that the extension registry records as agents, with no skills registered by any extension. Two memory-note pointers name files that do not exist.
Why it mattersA wrong project count sends the assistant looking for a project that is not there. A broken first-line pointer is the first thing it follows when a tool misbehaves. A directory listing cannot distinguish a working agent from a broken one.
RiskLow. Every item is a deletion or a header addition, and each is individually reversible.
EffortSmall to medium.
DecisionApproved — AI-005, AI-006, AI-007, AI-011, AI-013, AI-014

Where the assistant is being misled

  • Wrong counts. "Fifteen projects" against a solution of seventeen; "15 audit guardrails" against seventeen.
  • Wrong version. The XAML compiler note names Windows App SDK 2.3.1; the project references 2.4.0.
  • Wrong interpreter claim. The instructions say the Python launcher they tell the assistant to avoid is a broken store stub; it resolves and reports 3.13.15 here.
  • Wrong server location. The MCP reference table says the CSV server lives in one file; the authoritative registration is in another.
  • Obsolete rationale. The same table explains an absence using a tool-count ceiling that the workspace settings themselves record as removed.
  • Dead first step. Three files instruct the assistant to consult a troubleshooting note that does not exist.

Related checks that must be run by hand

Three repository checks are marked as manual-only, so no assistant can start them on its own. One overlaps this audit — agent-performance-audit looks at how the assistant behaves rather than how it is configured. It was not run, and none of its findings are claimed here. Run it directly if a behavioural review is wanted. The other two, winui-agent and workflow-edgecase-inspection, matter only if UI work is implemented later.

What improves after the approved work

A request starts with correct facts and no dead tool definitions. A code edit loads the guidance it needs and not a UI-automation procedure it will not use. A rule has exactly one home, so it can be changed once. The agents folder contains only files that load.

10. Final recommendations

  1. Start with truth. Phase 1 corrects five wrong facts, a broken first-line pointer and seventeen agent files that no tool can load. It changes nothing about how the application behaves, and every later phase depends on it.
  2. Then remove what cannot work. Two servers, 54 tool definitions, one duplicate registration and a sampling key aimed at a server that never starts.
  3. Then stop paying twice. About 6 KB of rules is currently loaded in two places. Consolidating it makes a rule change a one-line edit instead of a hunt.
  4. Finally, load the big procedure on demand. The UI-automation instruction is the single largest recurring cost in the repository — 27 KB matched by almost every code edit. Moving it behind a skill is the one change that will be felt on every task afterwards.
  5. Keep the reversibility. Every change is a text edit to a tracked file. If the assistant's behaviour worsens after Phase 3 or 4, revert that phase and keep the rest; the phases do not depend on each other's text.
Nothing was implemented. No package was installed or upgraded, no MCP server added or removed, no instruction, agent, skill or setting edited, and no source file touched. The only files this audit wrote are this report, its rendering source, and the specification in Dependency_Assessment/.
