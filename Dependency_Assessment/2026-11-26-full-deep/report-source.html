What this report is. A read-only assessment of the whole workspace. It states what was found, what was approved, and what the work would involve. It is not a record of work performed: no package was updated, no project, source, instruction or configuration file was edited, no database was contacted, and nothing was installed. The companion specification, DEPENDENCY_AND_MODERNIZATION_SPECIFICATION.md, is the implementation input for /speckit.specify.

1. Executive summary

The application is in good shape. It builds clean, it carries no known vulnerability, and the groundwork for its data access is sound. What this audit found is a different kind of debt: places where the repository has quietly drifted from its own rules, and places where hand-written code is maintaining something the platform already provides. None of it is on fire. All of it is cheap to fix now and expensive to leave.

0known vulnerabilities across every project, including transitive packages
1credential exposure: live-looking passwords committed in appsettings.json
32proposals raised, every one approved

Overall health

The build is clean: 0 warnings and 0 errors across 17 projects on .NET 10. No package in the graph sits in a vulnerable range, and the solution already pins its way out of two advisories that would otherwise appear on every restore. The 17 architecture guardrail tests assert real contracts, the database artifacts are complete (204 create scripts, 204 matching rollbacks), and the master SQL aggregates are byte-consistent with the 107 individual procedure files they are built from.

Three areas need attention, in this order. First, credentials are committed. The tracked configuration file carries a password inside two connection strings and a full Infor Visual server, user and password triple. The configuration system already supports supplying these from the environment, so the fix is to commit the shape and let each machine supply the values. Second, the platform is one major version behind and several packages are terminal or superseded — including a Community Toolkit line whose 7.1.2 release is the last it will ever have, while the repository has already adopted the successor line elsewhere. Third, the code re-implements infrastructure it already owns: about ten services open their own database connections instead of using the shared executor that carries the retry policy, and the shared executor itself still exposes an inline-SQL path that the repository's own "stored procedures only" rule forbids.

Update status

Nine update proposals cover 17 package movements. Two are worth doing first because they make the rest trivial: central package management (across 17 project files, the same product version is currently repeated up to 14 times) and package source mapping. After those, each version change is a one-line edit. The two largest moves are the Windows App SDK from 2.4.0 to 2.7.0 and DevWinUI from 10.8.0 to 11.1.0; both are framework-level and both carry a manual screen-by-screen review before they ship.

Security concerns

One, and it is the committed credentials above. There is no vulnerable package. The two advisories that would otherwise affect this graph are already suppressed by a deliberate version pin, and the audit shows why that pin can be retired once the SQL client moves to its current release. Separately, the NuGet supply-chain posture is thinner than it looks: no NuGet configuration is tracked at all, so every clone inherits whatever that machine happens to have, and the standard dependency-confusion guard is absent because nobody needed it yet.

Performance

Two real findings. The generic-request part search asks the plant system for results on every keystroke once the text is long enough — a burst of typing becomes a burst of round trips, and an older answer can land after a newer one. And two settings paths block the interface thread on an asynchronous call while the settings screen loads. Both are small, contained fixes. Three other things that looked like problems turned out not to be, and are recorded so nobody re-raises them: the picture-resolution loop is deliberately once per work centre, the localised labels are evaluated once, and the background handlers are covered by the application's global fault handler.

Modernization

Nine proposals. The best-value one costs almost nothing: the Community Toolkit 7.1.2 packages are used in exactly four files, and one of them — the Controls reference — has no control used from it at all. The rest are the kind of debt that accrues quietly: a data library that depends on a user-interface project, a shared library that ships a dialog control, the largest class in the repository at 2,623 lines, and a JSON layer that is entirely reflection-based.

User experience

No redesign is proposed, and the reason is deliberate: any layout change in this application must carry a rendered before-and-after design, and nothing found here justified that cost. What is proposed is correctness. The Setup review screen currently displays two internal resource identifiers to a production lead because the strings they refer to do not exist. Coil weights are formatted for a fixed culture and carry a hardcoded unit. And 140 visible sentences are typed directly into the layout files rather than into resources, which means the interface cannot be translated predictably.

AI development

The previous audit of this repository already cleaned up the AI environment, and its work stands: the broken tool servers are gone and the two always-loaded instruction files were corrected. Four things were left behind. An agent-facing configuration file still declares the platform as 2.3.1 when it is 2.4.0, and a memory note records the same wrong number as a reference fact — an agent that trusts either looks up the wrong documentation. A Spec Kit hook calls a Python launcher that does nothing on this machine. The repository declares no documentation server at all, so the capability the project's own rules require exists only because one workstation happens to have it configured globally. And the NuGet tooling server cannot analyse this solution — it fails on every tool with an assembly mismatch against the current .NET SDK, which is why every version figure in this report came from the command line instead.

Highest-value recommendations

  1. Take the credentials out of the repository and rotate the ones that have been committed.
  2. Adopt central package management, then move the eight packages that are behind.
  3. Retire the Community Toolkit 7.1.2 line — four files, one dead reference, no behaviour change.
  4. Close the inline-SQL path in the shared executor, so "stored procedures only" is true rather than nearly true.
  5. Fix the two interface stalls and the keystroke search burst, then add the two missing strings.
  6. Correct the three files that tell an agent the wrong platform version, and declare the documentation servers.

3. Per-package assessment

Windows App SDK — 2.4.0 to 2.7.0

Why it matters. This is the framework every screen runs on. Staying a major version behind means missing platform fixes and, eventually, losing the ability to take them without a much larger jump. Compatibility. Declared in 14 project files and resolved by all 17. Required work. The version change itself, then a manual pass of sign-in, the waitlist list and detail, setup, generic request, settings and the database deployment tool. Risk. WinUI control templates, theming and title-bar behaviour are the usual casualties. Effort. Medium, dominated by the review rather than the edit. Decision. Approved.

Microsoft.Extensions.* — 10.0.10 to 11.0.0

Why it matters. Five abstraction packages hold up the application's hosting, logging, configuration and dependency-injection stack. Compatibility. The 11.0.0 package manifest carries a net10.0 asset group, so the upgrade does not force a target-framework change — this was verified from the manifest rather than assumed. Required work. One version per project once central management exists. Risk. Configuration binding and logging filter evaluation are the two areas worth watching. Effort. Medium. Decision. Approved.

Microsoft.Data.SqlClient — 6.1.1 to 8.0.0

Why it matters. This is the driver behind every Infor Visual read, and it is also what makes the solution carry a security version pin it would rather not have. The current 6.1.1 drags in a cryptography package inside two known advisories; the solution pins a safe version to keep the build clean. Release 8.0.0 requires a newer cryptography package that is already outside those advisories, so moving to it retires the pin as a side effect. Caution. 8.0.0 was published on the audit date. It has no field history. Required work. Prove Infor Visual connectivity through the live path before it ships, and record the previous version so a revert is one line. Effort. Small. Decision. Approved, with that connectivity gate written into the plan.

MySqlConnector — 2.6.1 to 3.0.0

Why it matters. Every read and write against the three internal stores goes through this driver. A major release can change connection-string option handling, date and time mapping, cancellation behaviour and pool defaults. Required work. Validate every stored-procedure call path against the local instance before the plant host is touched. Effort. Medium. Decision. Approved.

DevWinUI — 10.8.0 to 11.1.0

Why it matters. A third-party control and composition library that overrides WinUI styles. Risk. The highest visual risk in this set: a major version of a styling layer can move any screen. Required work. Deliberately sequenced last among the runtime upgrades, with every screen reviewed. Effort. Medium. Decision. Approved.

Test stack — MSTest 4.5.3, Test SDK 18.12.0, coverlet 10.1.1

Why it matters. 2,768 test methods and 17 architecture guardrails run on this stack. MSTest 4 is a major release with changes to assertion overloads and data-driven tests. Compatibility. The current MSTest release targets .NET 9 rather than .NET 10; it runs on .NET 10 but ships no .NET 10 asset of its own, which is worth knowing rather than discovering. Required work. Green run and matching method count before and after. Effort. Medium. Decision. Approved.

Patch-level updates — WinUIEx, SDK BuildTools, ProtectedData

Three low-risk bumps grouped into one decision. No behavioural expectation beyond the documented fixes, and a revert is a version-line revert. Effort. Small. Decision. Approved.

Community Toolkit 7.1.2 — remove, and move the animation helper to 8.x

Why it matters. The 7.1.2 packages are the last release of a retired line; the successor line renamed every package and is already in use in this repository for the settings controls. The audit measured the real usage rather than the reference list: the Controls namespace is declared in two layout files and no control from it is used; the animation package supplies exactly two connected-animation extension methods, used in two files. Required work. Remove the dead reference, repoint the two call sites at the 8.x animation package, and confirm the waitlist-to-detail transition still animates. Benefit. Two terminal packages gone for four edits, and — as a follow-on — the restore workaround for the older graphics runtime can then be removed, because the remaining projects unify on the current version. Effort. Small. Decision. Approved.

4. Custom functionality and modernization

Data access that bypasses the shared executor

Existing behaviour. The solution has a shared database executor that carries retry policy, timeouts and failure reporting. About ten services do not use it: they open their own connection and command directly. Why it should change. Every bypassed site is a place where the retry behaviour, the timeout and the failure report are somebody else's problem. Benefit. One place to fix a connection problem instead of ten. Risk. Each caller must not lose behaviour the shared executor does not model. Effort. Medium. Decision. Approved.

The inline-SQL escape hatch

Existing behaviour. The shared executor still exposes a path that runs caller-supplied SQL text, and a query method that will read an unlimited number of rows. Why it should change. The repository's rule is that every data operation goes through a stored procedure, and a build-failing audit test enforces that in application code. This path is the blind spot that test cannot see. Benefit. The rule becomes true, and one unbounded-read risk closes. Effort. Small. Decision. Approved.

Two implementations of one Infor Visual query path

Existing behaviour. The same query service exists twice, in the core library and in the setup module. Why it should change. Read behaviour, fallback and timeout policy can drift apart in two copies. Risk. One of the copies may exist because of a host difference that is genuinely load-bearing. Effort. Medium. Decision. Approved.

Reflection-based JSON everywhere

Existing behaviour. About 22 files serialise with reflection, and each of the five store classes hand-builds its own serializer options. Why it should change. Source generation makes serialisation faster and removes a blocker for trimming. Benefit. Mechanical and low risk. Effort. Medium. Decision. Approved.

A data project that depends on a user-interface project

Existing behaviour. The generic-request logic library references the waitlist view library, and the generic-request data library references the waitlist wizard project. A data layer currently depends on a user-interface layer. Why it should change. The dependency direction should be one-way, and the generic-request flow should not drag the waitlist interface through its chain. Benefit. Correct layering. Risk. The largest blast radius on this list. Effort. Large, and it is deliberately placed in its own late phase. Decision. Approved.

A dialog control living in the shared library

Existing behaviour. A user-interface control is defined inside the library that is meant to hold no view types, so every library referencing it links interface code. Why it should change. The stated layering rule should be true. Effort. Medium. Decision. Approved.

The largest class in the repository

Existing behaviour. One settings view model is 2,623 lines with 106 public members, and its test file is 1,124 lines. Why it should change. It is the hardest file to review and a top-three churn target. Risk. The whole settings surface binds to it, so this is behaviour-preserving extraction rather than redesign. Effort. Large. Decision. Approved.

Hand-written animation

Existing behaviour. One control builds its own animation timeline while the toolkit's animation helpers are already referenced. Effort. Small. Decision. Approved.

6. Workspace-wide changes

Central package management

The same product version is currently written into up to 14 project files. One file holding every version once turns each of the eight version changes into a single line, and removes the possibility of two projects drifting onto different builds of the same package. This is the highest-leverage structural change in the set, and it must come before any version move.

Package source mapping

No NuGet configuration is tracked in this repository at all: git has never held one, so every clone falls back to whatever that machine happens to have and the feed set is not reproducible. Committing a configuration that declares one feed and maps each package to it fixes both problems at once — the feed set becomes shared, and the standard dependency-confusion guard exists before it is needed. The exposure today is low precisely because there is one feed; the guard costs four lines.

Two entries in the shared build properties file

Cross-project impact of the data-access work

The shared executor is referenced by five projects, so tightening it to stored procedures only and routing ten further call sites through it touches persistence across the application, the setup module, the mock mirror and the mock service. It is the one change in this set that no single project owns.

A real risk that is not code

Removing the committed credentials means each host must be given its values before it can start. That is a deployment step, not a code change, and it belongs with whoever provisions the plant machines. The application must fail loudly with the variable name if one is missing — never fall back to an empty connection string.

What is out of scope, and why

  • Any interface redesign. A layout or interaction change in this application must carry a rendered before-and-after design. Nothing found justified that cost.
  • The unreferenced resource keys. Deleting about 298 keys would trade a maintenance gain for a runtime-regression risk, because some keys are composed at run time.
  • The Spec Kit catalogue size. 90 agent files and 61 prompt stubs cost metadata only, and the previous audit already removed what could not load.
  • The user-level editor configuration. User instruction files, global tool servers and installed extensions were not audited.
  • Any live store. No database connection was opened and no plant host was contacted.
  • Engine, ORM or framework migration, and any benchmark. No performance figure in this report is measured; two behavioural requirements are stated with a stated way to measure them.
  • Historical specification documents that cite the older platform version. They record what was true when written.

10. Final recommendations

Do these first — highest value per hour

  1. Take the credentials out of the repository. Commit the shape, supply the values per host, fail loudly when one is missing, and rotate the values that have been committed. Nothing else in this report changes a security posture as much for as little work.
  2. Adopt central package management, then move the packages. One file for versions, then eight version changes that are each a single line. This is the change that makes the rest of the list cheap, including next year's.
  3. Retire the Community Toolkit 7.1.2 line. Four files, one dead reference, one terminal package line, and it unlocks the removal of a build workaround whose own comment predicted this.

Then close the rule gaps

  1. Close the inline-SQL path in the shared executor and route the ten bypassing call sites through it. Two proposals that turn "we use stored procedures" from a convention into a property of the code.
  2. Fix the two interface stalls and the keystroke search burst. Small, contained, and each one is felt by a person using the application rather than measured in a profile.
  3. Add the two missing strings on the Setup review screen. A production lead should not be shown an internal identifier in place of a word.

Then the structural work, in its own phases

  1. Break the data-to-interface dependency and move the dialog out of the shared library. These are the two changes that make the layering rule true, and they are large enough to deserve their own review cycles.
  2. Split the largest class. 2,623 lines is not a crisis, but it is the file every settings change walks through.
  3. Extract the visible sentences into resources. 140 attributes, no pixels moved, and the interface becomes translatable on a predictable convention.

A closing note on what was not found

This audit looked for problems and, in several places, found none. There is no vulnerable package. There is no project-reference cycle. The database artifacts are complete and the master aggregates are consistent. The architecture guardrails assert real contracts. The shared database executor already exists and is well designed — the work is to finish adopting it, not to invent it. A modernization report that only lists findings overstates how much is wrong; the state of the floor matters as much as the state of the roof.
