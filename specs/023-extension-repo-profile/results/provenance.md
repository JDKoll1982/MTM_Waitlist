# Provenance of every expected-answer record

This file records one decision and the procedure it changes. It exists because FR-030 rules out the
method the first record was written by, and because a record whose provenance is not written down
cannot be told apart from one written to agree with the run it judges.

## The decision: records come from the inspection surface

`research.md` R12 and `plan.md`'s "How one checkout is proven" step 1 are **superseded by FR-030**.
Both describe a record written by reading a checkout's declarations and markup by hand. That method is
retired, and the reason is the one the spec gives: the attempt made so far — a purpose-written,
regex-based script — reproduced the layer counts exactly (1051 declared types, split 82 view, 76
viewmodel, 475 service and 418 model) and still disagreed on the findings, reporting 29 where the
analysis reports 21. A derivation that can agree on three quarters of the answer and disagree on the
fourth proves nothing about the quarter it got right, because it is a second, unpublished reading of
the same repository rather than a statement of what the published one will say.

From this point on, every record under `expected/` is produced by the extension's own inspection
surface:

```bash
node out/validate.js <checkout> --expected <record.json>
```

`--expected` takes the checkout's inspection from `inspectFolder` — the same derivation the setup
prompt and the compatibility facts are built from — compiles the conventions the checkout's profile
declares, and writes the record in the shape `contracts/expected-record.schema.json` describes. No
record is written, extended or corrected by a second script, and no record is edited after a measured
run has been compared with it.

## The fresh-context procedure, amended

Each fresh-context profile run (T067, T070, T073 and T076) is handed **its checkout's `--inspect`
output beside the setup prompt, and no other description of the format**. The prompt states the
contract; the inspection states the facts. Neither is a replacement for the other, and nothing else —
no plan, no record, no summary of a previous run — is put in front of the author.

This is why `--inspect` is a supported mode rather than a debugging aid: the evidence a record is
produced from and the evidence an author is given must be one derivation, or the two answers drift.

## Tooling an author still adds

An author whose repository needs evidence the supplied inspection does not report may add tooling of
their own, as SC-016 allows. When that happens the addition is recorded **here**, with the evidence it
was needed for, and the profile it helped produce still imports with zero problems and still faces the
same comparison as any other. As of this writing no such exception is recorded: every record under
`expected/` names the inspection surface in its `source`, and no script outside the extension remains
that a record or a profile depends on.

`tools/derive_expected.py` and its `tools/__pycache__/` directory were deleted once all four records
had been produced by the surface, and the folder they lived in went with them. The four files under
`expected/` — `mtm-waitlist.json`, `mtm-wip.json`, `winui3-learning-lab.json` and
`mtm-receiving-application.json` — each open with `Produced by node out/validate.js --expected, the
inspection surface of csharp-xaml-graph 0.6.0`, so no record's provenance is anything else.

## Where the rollup reads this

The four-of-four rollup in `specs/023-extension-repo-profile/validation.md` (T080) carries each
record's provenance: for every checkout it states that the record was produced by the inspection
surface, before the first measured run, and names any deviation. A result whose record cannot be
traced to the surface is not evidence of the checkout, and the rollup says so rather than counting it.
