# Contract — Waitlist request actions

The interface this feature exposes to a caller and that a test codes against. Every identifier below is
exact: the strings are copied from the spec and from the code they bind to, and none may be renamed,
recased or pluralized downstream.

---

## C1 — View-model surface (`WaitlistViewViewModel`, `WaitlistViewDetailViewModel`)

The **list** view model exposes the four commands, generated by `[RelayCommand]` from an
`…Async`-suffixed method, which means the bound name **drops** the `Async` suffix
(`AcceptRequestCommand`, not `AcceptRequestAsyncCommand`).

| Command | Bound name | Parameter | Calls |
| --- | --- | --- | --- |
| Accept | `AcceptRequestCommand` | the row (`SampleOrder`) | `IWaitlistRequestService.AcceptAsync(requestId, employeeNumber, employeeName)` |
| Complete | `CompleteRequestCommand` | the row | `IWaitlistRequestService.CompleteAsync(requestId, employeeNumber, employeeName)` |
| Release | `ReleaseRequestCommand` | the row | `IWaitlistRequestService.ReleaseAsync(requestId, employeeNumber, employeeName)` |
| Cancel | `CancelRequestCommand` | the row | prompts, then `CancelOwnRequestAsync` when the viewer is the requester, else `TransitionStatusAsync(requestId, "Canceled", reason, employeeNumber)` |

**Release has no surface.** `ReleaseRequestCommand` is kept and tested because releasing is the only way to
put a claimed request back on the open list, but **no card and no page binds it** — see C7. A future change
that surfaces it must bind this command rather than add a second one.

**The detail view model exposes no action command at all** (FR-025). It exposes the send-message command →
`IWaitlistRequestService.UpdateNoteAsync(requestId, note, actorEmployeeNumber, actorEmployeeName)`, the
history read, and `RefreshInterval`. There is exactly one surface that decides what a viewer may do to a
request, and it is the card.

**The send-message command has no role gate** (FR-012, revised after the first build). It was gated on the
handler role; the floor could not tell a handler anything, so the gate was removed from both the command and
the markup. The only gate left is that the message must actually contain something.

**Rule**: a command's parameter is always the row, and the row must carry `RequestId`. A row without a
request id is not actionable and its gates are all false.

## C2 — Prompt seam (`IWaitlistRequestActionPrompt`)

```csharp
Task ShowWarningAsync(string title, string message, string closeText);
Task<bool> ConfirmAsync(string title, string message, string acceptText, string cancelText);
Task<string?> RequestCancellationReasonAsync(string title, string message, string confirmText, string cancelText);
```

- `ShowWarningAsync` — an acknowledgement-required message. Returns once it has been dismissed. With no
  XAML root it returns immediately rather than throwing; the caller must already have recorded the refusal
  elsewhere so nothing is lost when no dialog can be shown.
- `ConfirmAsync` — `true` only when the primary button was chosen.
- `RequestCancellationReasonAsync` — the reason text when the primary button was chosen, `null` when the
  prompt was dismissed. An empty string is a valid answer: it means "confirmed, no reason given", which
  is **not** the same as a dismissal.
- With no XAML root (a headless host) the implementation must answer `false` / `null` — it must never
  throw and must never auto-confirm.

## C3 — Offered actions per viewer and state

Gate inputs, exactly as the service computes them:

| Gate | Predicate |
| --- | --- |
| may handle requests | `RequestActionPolicy.CanViewerHandleRequests(role)` — role is one of `Material Handler`, `Production`, `Production Lead`, `Setup`, `Setup Lead`, `Plant Manager`, `Admin`, `Developer`, case-insensitive |
| may accept | `RequestActionPolicy.CanViewerAccept(status, mayHandleRequests)` |
| may complete / release | `RequestActionPolicy.CanViewerCompleteOrRelease(status, assignee, viewerEmployeeNumber, mayHandleRequests)` |
| may cancel | the viewer is the requester (`RequesterEmployeeNumber` equals the viewer, case-insensitive) **and** the row is still waiting — **or** the viewer is the assignee |

| Viewer | State | Offered |
| --- | --- | --- |
| handler-or-above | `Pending` | Accept + Cancel when the viewer raised it; Accept alone otherwise |
| handler-or-above, the assignee | `Accepted` | Complete + Cancel |
| handler-or-above, not the assignee | `Accepted` | — |
| handler-or-above | `Completed` or `Canceled` | — |
| not handler-or-above | any | — |
| the requester | own row, `Pending` | Accept (if also a handler) + Cancel |
| the requester | own row, `Accepted` by someone else | — |

**Two invariants the card is designed around**, and both are asserted by tests:

1. **Accept and Complete are never both offered.** They are the same button in two states: the primary
   action is Accept while the request is available and Complete once the viewer has claimed it.
2. **Cancel is offered whenever Complete is.** Refusing work you have taken is as available as finishing it.

Buttons are **hidden**, not disabled, when their gate is false. `OfferedActionCount` counts the true gate
flags, and a test asserts the number of non-null commands equals it in both directions — a flag with no
command and a command with no flag are both failures (FR-020).

## C4 — Refusal vocabulary

A refusal must be a plain sentence, localized, and must name what could not be done. The screen reports
it as `ActionRefusalMessage`; it is never a silent no-op and never a raw exception message.

| Situation | Message intent |
| --- | --- |
| Accept refused — another handler got there first | the request was already taken by another handler; choose a different request. **Shown as an acknowledgement-required warning, not only as a line on the list** (FR-024, key `Waitlist_Action.Refused.AcceptTaken`) |
| Accept refused — the request has left the list | the request is no longer on the list; choose a different request. Shown the same way (key `Waitlist_Action.Refused.AcceptGone`) |
| Complete / Release refused | the request is not assigned to you, or is already finished |
| Cancel refused | only the person who raised the request may cancel it, and only while it is waiting |
| Store unreachable | the existing per-screen unavailable state and its manual retry — not a success message |

**The store arbitrates, the screen only reports.** On a lost claim the screen reads the request back and
reports what actually happened: a request still on the list but no longer available was taken by another
handler, while a request the store no longer knows about has left the list. Neither is reported as success,
and neither alters the winning claim.

## C5 — Stored status and event vocabulary

| Kind | Exact values |
| --- | --- |
| Stored status | `Pending`, `Accepted`, `Completed`, `Canceled` |
| Display-only badge text | `Waiting`, `In Progress`, `Done`, `Cancelled` — never compared, never stored |
| Audit event | `Created`, `Accepted`, `Completed`, `Released`, `Canceled`, `NoteUpdated`, `StatusChanged` |
| Release marker | `Released` event + `ReleasedUtc` + `AssignedMaterialHandler` cleared; status stored as `Pending` |

`Done` (FR-006) is the display label for the stored status `Completed`; the audit event is `Completed`.
Nothing writes either `Done` or `In Progress` to the database.

## C6 — Stored-procedure surface

Every action reuses:

- `sp_waitlist_request_list` — read, `p_building`, `p_include_resolved`
- `sp_waitlist_request_status_update` — write, `p_public_id`, `p_status`, `p_assigned_material_handler`,
  `p_cancellation_reason`, `p_canceled_by_employee_number`, `p_note`

and the feature adds exactly one procedure, the read half of the audit trail (T037):

```sql
CREATE PROCEDURE sp_waitlist_request_audit_list(IN p_request_public_id CHAR(36))
```

returning `id`, `public_id`, `request_public_id`, `from_status`, `to_status`, `event_type`,
`actor_employee_number`, `actor_employee_name`, `details`, `occurred_utc` for one request, ordered
`occurred_utc ASC, id ASC` — **oldest first**, so the page renders them in the order they happened without
re-sorting. Paired `create.sql` / `rollback.sql`, block appended to `Database/StoredProcedures/AllSPs.sql`.

Every read and write goes through `ExecuteStoredProcedureQueryAsync` / `ExecuteStoredProcedureNonQueryAsync`
on `MySqlDatabaseTarget.MtmWaitlist`. No inline statement text is added anywhere (constitution III), and
`InlineSqlAuditTests` fails the build if that changes.

## C7 — Markup contract for the card

The action area of `Module_Waitlist/Controls/WaitlistLineCardView.xaml` carries at most two icon
buttons at once, side by side in the existing vertically-centred area above the compact status pill:

| Aspect | Value |
| --- | --- |
| Button size | `MinWidth`/`MinHeight` 44, matching the removed pair |
| Command | bound from the row — never absent |
| Visibility | bound one-way to the row's gate flag |
| Accessibility name | bound to the row's localized action text; no literal `Cancel`/`Accept` string in markup |
| Tooltip | bound to the row's localized action text as well, so the action is named on hover as well as to a screen reader |
| Accept | background `SystemFillColorSuccessBrush` (green), glyph **`E8FB`** (Accept) |
| Complete | background `AccentFillColorDefaultBrush` (accent), glyph **`E930`** (Completed) |
| Cancel | background `SystemFillColorCriticalBrush` (red), glyph `E10A` (Cancel) |
| Release | **not drawn** |
| New-message marker | a 26×26 black circle with `E8BD;` (Message) on the lower-right of the request-type image, `Visibility` bound to the row's `HasNewMessages`, tooltip bound to `NewMessageTooltip` |
| Status badge | background and text both bound through `RequestStatusToBrushConverter` off the row's stored `Status`; one colour per state (see below) |
| Anatomy | image 96×96 fixed; title own row; four metadata rows; per-type detail grid; status pill fixed ~36px height below the buttons |

### Status badge colours (`RequestStatusPalette`)

| Stored status | Badge text | Colour |
| --- | --- | --- |
| `Pending` | Waiting | mid grey `#5F6670` |
| `Accepted` | In Progress | blue `#0F6CBD` |
| `Completed` | Done | green `#107C10` |
| `Canceled` / `Cancelled` | Cancelled | red `#C42B1C` |
| anything else | *(no badge)* | transparent — `HasStatusBadge` hides the pill |

The palette exposes its colours as `Windows.UI.Color` as well as brushes, so the mapping is testable without a
XAML runtime, and a test asserts every colour clears the WCAG AA 4.5:1 contrast ratio against the badge text.

**Why not the `SystemFillColor*` theme tokens?** They are the obvious choice and they are wrong here: they are
built to carry a *dark* glyph on top, the way an `InfoBar` uses them for a severity icon. `SystemFillColorCaution`
is `#FCE100`, on which white text is unreadable. These values are the accessible Fluent equivalents instead.

**`Done` and `Cancelled` are currently unreachable on the list.** `WaitlistViewViewModel` builds its rows from
`GetActiveRequests` alone, which returns `Pending` and `Accepted` only, so a resolved request never reaches the
card and those two colours cannot be seen there — the "Show only my requests" toggle filters that same active
set. They are implemented, mapped and tested so that wherever a resolved request *is* drawn it is coloured
consistently; surfacing resolved requests on the list is a product decision, not part of this contract.

Glyph names are taken from the [Segoe Fluent Icons list](https://learn.microsoft.com/windows/apps/design/style/segoe-fluent-icons-font).
The **E0–E5 range is deprecated** by that list, so `E10B` (the earlier Accept glyph) is not used.

**Accept and Complete must be unmistakable.** They occupy the same slot in two states, so they differ in
both colour and icon — green with a bare check for Accept, accent with a circled check for Complete. A test
asserts both differences, so a future edit cannot quietly collapse them back into one control.

No button may be drawn in this area without a `Command`, a `Visibility` gate and a tooltip.

The **request detail page must draw none of these buttons** (FR-025). `RequestPage_DrawsNoActionButton`
scans `Module_Waitlist/Views/WaitlistViewDetailPage.xaml` for a binding to any of the four commands and
fails if one appears.

## C8 — History and new-message contract

| Aspect | Value |
| --- | --- |
| Read | `IWaitlistRequestService.LoadAuditTrailAsync(requestId, ct)` → store rows **merged** with the in-session trail, deduped by `occurredUtc truncated to seconds \| eventType \| employeeNumber \| details`, oldest first. The truncation is required: `occurred_utc` is a whole-second MySQL `datetime` while the session stamps sub-second precision, so comparing full precision rendered every entry twice (T043) |
| Read failure | the in-session trail is returned unchanged — a failed read is **never** rendered as "no history" |
| Empty | the block renders for an empty history and says so (`IsHistoryEmpty`, `HistoryEmptyText`); it does not hide |
| History row | three columns: occurrence (local), **sender full name** (`System` when the entry has no person), message text. The internal event type is not shown (FR-013) |
| Seen marker | `IWaitlistMessageSeenStore.MarkSeenAsync(requestId, newestEntryOccurredUtc)` — the newest **entry**, not the current clock |
| Indicator | `HasNewMessages` = the request's `LastMessageUtc` (from the queue row's `last_message_utc`) is newer than the stored marker. A request with no marker, or with no human message at all, is not flagged — the value only moves for an authored `NoteUpdated` (FR-028) |
| Refresh | `WaitlistViewDetailViewModel.RefreshInterval` = 30 s; the page reloads the request and its history on that cadence while it is open |
| Dispatcher | the refresh timer is taken from the injected `DispatcherQueue` or, failing that, from `DispatcherQueue.GetForCurrentThread()`; if neither yields a usable timer the page stays static and **logs why** rather than appearing to refresh |
| Draft safety | the message box pushes every keystroke (`UpdateSourceTrigger=PropertyChanged`) and a refresh never seeds the box over an unsent edit, so a message is stored from what the viewer typed and never lost to the page's own timer (FR-012) |

Both timestamps are UTC and both arrive from the same store read, so the comparison compares like with like
(verified against the database — see the defect record and T044).
