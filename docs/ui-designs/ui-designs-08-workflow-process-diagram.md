# Prompt 8 — Workflow / process diagram

Copy this whole file into the task. Replace the `<<…>>` placeholders in section 2.

You are producing or updating a **print-ready workflow diagram** for the MTM Waitlist Application. The
diagram is built by this repository's pipeline from a JSON spec — never by an image-generation model, never
by hand-editing a `.dot` file or a PDF.

---

## 1. Purpose

Explain a workflow truthfully: which screen starts it, which commands run, which services and stored
procedures are called, where a decision branches, what each outcome is, and which parts are worth fixing.
The diagram is both documentation and an input to refactoring work, so it must be correct, printable and
editable at its source.

## 2. Required inputs

- `<<WORKFLOW>>` — a manifest id: `workorder-new-request`, `workorder-workcenter-setup`,
  `generic-new-request`, `generic-workcenter-setup`, or a new one.
- `<<VARIANT>>` — `engineer` (class names, commands, services, procedures) or `friendly` (plain language).
- `<<SHEET>>` — the sheet being added or changed; a whole document when it is new.
- `<<FINDING>>` — the refactor finding, when the change is a finding rather than a flow.
- `<<REFACTOR>>` — when the diagram supports a QOL design record, that record's refactor name.

Read, in this order:

1. **The current digest**, read-only — sheets, lanes, nodes, edges, findings and connectors, with the `.dot`
   files checked against the spec:
   `python docs\diagrams\tools\diagram_context.py --workflow <<WORKFLOW>> --sheet <<SHEET>>`
2. **The manifest**, `docs/diagrams/tools/manifest.json`, which maps each workflow and variant to its spec
   and PDF and fixes sheet order.
3. **The spec**, `docs/diagrams/tools/spec-diagram-<<WORKFLOW>>[-friendly].json` — the source of truth.
4. **The code**, for every label: the XAML view, the view model and its commands, the service interface,
   and the stored procedure's `create.sql` under `Database/`.
5. **The authoring rules**, `.github/instructions/diagram-authoring.instructions.md`, and
   `docs/diagrams/README.md`.

## 3. Analysis instructions — what each file is responsible for

| File | Responsibility | Who writes it |
| --- | --- | --- |
| `tools/spec-diagram-*.json` | **Source of truth.** Per sheet: title, source note, lane order and titles, nodes as `[id, label, kind]`, edges as `[from, to, label, style]`. | You, by hand. |
| `tools/manifest.json` | Which spec builds which PDF, in what order, and which workflow and variant each document is. Sheet numbering (`Sheet X of Y`) is computed from spec order. | You, only when a document is added or removed. |
| `dot/*.dot` | Generated by `dotgen.py`. A valid Graphviz description of **one sheet** — an inspection aid, not a deliverable. Regenerated on every build; a hand edit is lost. | `dotgen.py` only. |
| `pdf/*.pdf` | Generated by `render_sheets.py` **from the spec, not from the `.dot`**. The print-ready deliverable. | `render_sheets.py` only. |
| `tools/diagram_context.py` | Read-only digest for an agent. | — |
| `tools/verify_pdfs.py` | Asserts the print contract on every page and writes 300 DPI PNGs to `%TEMP%\mtm-diagrams\png`. | — |

Graphviz is **not** in the rendering path for the deliverable, and `dot -Tpdf` produces a single-page
automatic layout, not the paged print output. Graphviz is only for looking at one sheet by hand.

Record before editing:

- **The flow as the code runs it.** Every step is a call, a gate or a write that exists. Where the diagram
  and the code disagree, report both — never quietly redraw the diagram to match a change you made.
- **The lane each node belongs to.** This repository's pages use four columns left to right: `ui` (XAML
  views), `vm` (view models and commands), `svc` (services through DI), and a data column carrying `db`
  (stored procedure), `erp` (Infor Visual read) and `mirror` (`mtm_mock` fallback). Flow moves down a
  column and right across.
- **The seams.** A flow too large for one sheet is split at an architectural seam — UI and validation on
  one sheet, services and stores on the next — never shrunk to fit.
- **The findings.** Each `refactor` node is one finding, with the class and method it refers to, and it
  also appears in `docs/diagrams/diagram-workflow-refactor-notes.md`.

## 4. Generation instructions

### Engineer variant

1. Check `git status` and the working diff first, so you do not build on top of uncommitted work.
2. Edit the JSON spec. Use the node kinds exactly: `ui`, `vm`, `svc`, `db`, `erp`, `mirror`, `dec`,
   `note`, `refactor`, `conn`. Write deliberate breaks as `\n` inside the string, keep a line under about
   30 characters and a node under five lines, and put one idea per node — a label that needs "and" is
   usually two nodes.
3. Give every edge its real meaning and style. An edge that no longer exists is removed; a new gate is a
   `dec` node with both branches drawn.
4. Cross-sheet continuity uses off-page connectors **on both halves**: `[To Sheet 3]\nSubmitAsync` on the
   sheet that leaves, `[From Sheet 2]\nSubmitAsync` on the sheet that arrives. Pages are joined on the
   command name, not the page number.
5. Findings go in a `refactor` node on the sheet that shows the code, and get the same finding in plain
   words on the friendly sheet.

### Friendly variant

Plain language for the people who use the screens: no class names, method names, procedure names or
interface names. The same steps, branches, outcomes and finding count. A friendly sheet never carries
information the engineer sheet lacks and never omits a branch.

### Build and render

```powershell
python docs\diagrams\tools\dotgen.py docs\diagrams\tools\spec-diagram-<<WORKFLOW>>.json
python docs\diagrams\tools\render_sheets.py docs\diagrams\tools\manifest.json
python docs\diagrams\tools\verify_pdfs.py
```

`dotgen.py` accepts any number of specs; rebuilding all 24 sources is a loop over `tools\spec-*.json`.
`verify_pdfs.py --no-png` skips the 300 DPI export when only the assertions are needed.

### Tying it to a QOL design record

When the diagram supports a design record, its `workflow_refs` must name the same sheet and node ids, for
example `{ "sheet": 1, "nodes": ["v_wc", "d_gate"] }`. `verify_designs.py` fails when a reference points at
a sheet that does not exist or a node id that is not on it — so update the record in the same change as the
spec.

A proposal references the PDF by relative link (`../../diagrams/pdf/<document>.pdf`). Do not copy the PDF
into the design folder. Only if a proposal must inline a still, export the 300 DPI PNG of that sheet into
the design folder as `<refactor>-workflow-<document>-sheet-<n>.png`, and delete it if the proposal later
stops needing it.

## 5. Visual standards — the print contract

Requirements, not preferences. A sheet that breaks one is not finished.

| Rule | Value |
| --- | --- |
| Page | 792 × 612 pt — 11 in × 8.5 in, landscape |
| Margin | 0.5 in clear on all four sides; header rule at y = 49, legend rule at y = 555.5 |
| Type floor | 9.5 pt effective on every label, edge annotation and legend item; node labels at 11 pt wherever the sheet allows |
| Shapes | 12–16 per sheet |
| Canvas | pure white `#FFFFFF`, ink `#111111`, pastel fills, 1.5 pt borders |
| Every page | title header, `Sheet X of Y`, shape legend |

Colour meaning is fixed and repeated in the legend: blue view, purple view model, amber diamond decision,
teal service, grey stored procedure, tan Infor Visual read, pink cache mirror, red dashed finding, blue
dashed off-page connector. The shapes differ as well as the colours, so the pages survive grayscale print.

## 6. Accuracy requirements

- Every class, command, service and procedure name is read from the repository in this session — never
  recalled.
- One node, one idea. No combined steps that hide a branch, and no branch without both outcomes.
- A finding names the class and method on the engineer sheet and the consequence for the operator on the
  friendly sheet.
- The diagram never asserts behaviour the code does not have. A broken guard is a `refactor` node, not a
  working step.
- Cross-sheet badges name the same command on both halves.
- No invented lane, node kind or decorative icon.

## 7. Technical requirements

| Item | Requirement |
| --- | --- |
| Source | JSON spec under `docs/diagrams/tools/`; `.dot` and PDF are build output |
| Deliverable | PDF in `docs/diagrams/pdf/` from `render_sheets.py` |
| Evidence | `verify_pdfs.py` passes every page; the 300 DPI PNG of the changed page was looked at |
| Dependencies | PyMuPDF, the Segoe UI face that ships with Windows; Graphviz only for hand inspection |
| Design record | `workflow_refs` resolve, and `verify_designs.py --all` stays clean |

## 8. File naming

Sources and output keep the pipeline's own names:

```
docs/diagrams/tools/spec-diagram-<workflow>[-friendly].json
docs/diagrams/dot/diagram-<workflow>[-friendly]-<n>-<slug>.dot
docs/diagrams/pdf/diagram-<workflow>[-friendly].pdf
```

A still inside a design folder, only when one is unavoidable:

```
docs/ui-designs/<workflow>/<screen>/<refactor>-workflow-<document>-sheet-<n>.png
```

## 9. Validation checklist

1. **Digest.** `diagram_context.py --workflow … --sheet …` shows the sheets, nodes, edges and connectors
   you intended, and reports no missing source.
2. **Build.** `dotgen.py`, then `render_sheets.py`, then `verify_pdfs.py`, in that order.
3. **Print contract.** Every page at size, in margin, at or above the type floor, 12–16 shapes.
4. **Look at the page.** Open the 300 DPI PNG of the changed page from `%TEMP%\mtm-diagrams\png`. A label
   on a border, an arrow crossing a box or a lane frame cutting a node means it is not done.
5. **Names against code.** Re-read every class, command and procedure name in the diff against the file
   that declares it.
6. **Both variants.** A changed step appears in the engineer sheet and the friendly sheet; a changed
   finding appears in both and in `diagram-workflow-refactor-notes.md`.
7. **Cross-sheet pairing.** Every `[To Sheet N]` has a matching `[From Sheet M]` naming the same command.
8. **Design records.** `python docs\ui-designs\tools\verify_designs.py --all` still passes, so no
   `workflow_refs` entry was left pointing at a node that moved.

## 10. Acceptance criteria

- The source is a JSON spec, the PDF came from the renderer, and the `.dot` is reproducible.
- Every page meets the print contract, verified rather than assumed.
- Every label traces to a file in this repository as it exists now.
- The friendly and engineer variants cannot disagree: same steps, same branches, same findings.
- The findings are in the refactor notes, so a `/speckit.specify` run can consume them.
- Nobody has to open Graphviz to read the deliverable, and nobody has to read PDF bytes to change it.
