1. The headline: a work center without a work order can raise a request

Until this month the application could only raise a request against a work order. A work center that had no job — or a job that had not been released — had no way to ask for anything. The plant needed a route for those cases, and it needed the request to be as trustworthy as one made from a work order.

That route now exists. It is called a generic request, and it is a complete flow from start to finish.

How it is set up

A work center is marked as a generic work center in the Setup screen. The designation is chosen inside the work center's Add or Edit form and is saved with the rest of the work center, so it is written once rather than the moment a switch is touched. A marked work center shows a badge wherever work centers are listed.

Because a generic work center has no work order, the application says so plainly: opening one from Setup stops with an explanation instead of starting a job step that has nothing to read.

How a request is raised

  1. Category. Pickup, deliver or other, drawn as cards. These are the same three the work-order flow offers; the fourth, assist, is deliberately absent because a request for help with a thing belongs to a job that says what the thing is.
  2. Item. What is being asked for. The four finished-product pickups — finished goods, non-conforming stock, work in process and outside service — are folded into one Finished Product card that opens a page asking which kind it is.
  3. Part and sequence. The requester states a part, the application proves it against Infor Visual and lists the sequences that belong to it as cards. The sequence chosen decides which system owns the quantity, and the screen says so in words rather than naming an internal system.
  4. Dunnage. Where dunnage is asked for, the plant's real catalogue is shown as a page, with pictures, a filter and a remembered choice. The same catalogue now backs the existing substitute dialog, so both surfaces show one thing.
  5. Scrap type. Where scrap is being picked up, the requester states the type. Each type is offered as a card naming only the type, and the stated type is what the request is about, so two types raised at one work center are two requests rather than one refused as a duplicate.
  6. Die. Search Infor Visual by die number or by part number. A part with several dies lists every die with the location it lives in; choosing several raises one request per die.
  7. Review and result. A review that lists only the stages the request actually has, then a result page that reads like the work-order result page: the same wording per outcome, and Retry that asks the queue again rather than redrawing the same failure.

What a generic request looks like afterwards

The request appears on the board as a row drawn with its own card, and opens a detail page. A die request reads its part first with the die in brackets — Pickup Die: 24733467-PKG - (FGT0150-01) — so the handler sees which part the die makes and which die to fetch in a single read. A die found by its own number keeps its number alone rather than showing an empty bracket.

Filling a request from a job that happens to be running

A generic work center that is running a job is now offered the chance to fill the request from it. Accepting seeds the job's part, sequence, die and dunnage as candidates that are then proved by the read that owns each one. Declining changes nothing, and the question is never asked twice in one request.

A filled request stays a generic request. The job is recorded as provenance rather than as the request's identity, and the detail page shows it as such, so nothing downstream confuses it with a request raised against a work order.

Why this matters

A work center with nothing scheduled can now be supplied. Before, the only choices were to raise the request against a work order that did not exist, or to walk to the crib.

2. What changed on the screens

Raising a request

  • Category cards. The category step is drawn as work center cards: a bordered surface with the name, a divider and the description, and an accent outline on the chosen card. Continue waits for a choice. Changing the category discards the item and everything asked below it, the way changing the work center already did.
  • Sequence cards. The part step puts the sequences beneath the part number box, one card each, with the chosen card outlined and ticked.
  • A coil or flatstock request reads as one part. A coil or flatstock pickup or deliver shows the part number, its on-hand rounded up and its description in one detail card, and skips the details step, because the requester is after the coil itself and not a sequence.
  • Search that collapses. Typing in the work center search opens the other work centers and clearing it closes them again, so a search shows every match rather than only this computer's own cards. The Setup screen's work center search now behaves the same way.
  • The details step asks how many, not what. The free-text description question is gone from the details step.

Setup

  • The review reads as sentences. A review with no scrap, or one with subordinate parts, now reads a sentence with the value in it rather than showing a resource key name where a word belongs. The dunnage and job-context sections carry descriptions and empty states of their own.
  • The generic designation lives in the work center form. It is chosen while editing the work center and saved with it, and it resets to off when no work center is selected so it can never offer a write for a work center that was not chosen.

Starting the application

  • The people who signed in before are offered. The sign-in surface lists the accounts that last signed in, read from a new procedure, so a returning operator picks a name instead of retyping one.
  • The picture cache reports its progress. The picture cache step runs first in the launch group, reports every 25 files on the splash's progress line, and logs a warning once it takes two seconds or more. A slow start now says where the time went instead of looking like one long wait.
  • The launch machine setup and sign-in appear on their own. A picture-copy notice used to hold every surface that says nothing about pictures, machine setup included. That is the one surface it must never stand in front of, because a computer the store does not hold cannot be used until it is set up. The decision now lives in a named policy that can be tested without a window, and the hold only applies while the launch window is still the surface on screen.

Waiting, and what the board shows

  • Completed requests stay reachable. The list now asks for resolved rows inside a retention window read from the setting waitlist.resolved_retention_days (seeded at 90 days), so a request that was completed no longer disappears from the session on the next refresh. The board itself still draws pending and accepted requests only, and the read is bounded at the database rather than fetched and discarded in the application.
  • Card labels. The card gained labelled cells for part, sequence, on-hand and on-hand-by, a named source per inventory system, an explicit "die location missing" state, and a "lugger unavailable" state, so a missing value says so instead of drawing blank.

Dialogs

  • One surface, not two. The standard message dialog body used to wrap itself in a card, so a warning or confirmation showed a second surface inside the dialog while every other modal in the application draws straight on the dialog. It now matches the work center form, the computer editor, the lugger editor and the part stock window.

3. For the people who install and run it

The database install scripts are gone, replaced by a tool that shows you first

The retired installer applied a bootstrap whose first statement dropped mtm_waitlist, so a store that was one deployment behind came back empty. It has been replaced by a three-step deployment tool that reads the object tree directly, shows what differs, and only removes what an operator confirms on a screen that names the object.

  • It copies before it writes. Every table goes into {database}_backup before the first statement, and the run stops if a copied table holds fewer rows than its source. On a host with binary logging off, that copy is the only undo a deployment has.
  • It can duplicate a database on request. Step one offers "Keep a copy of this database", which carries tables with their keys, indexes, comments and auto-increment, every row, the views (re-pointed at the copy), the routines and the triggers.
  • It is scoped by database name. mtm_waitlist* deploys from one tree, mtm_mock* from another, and anything else is refused. The tool used to have one tree and write it wherever the picker pointed.
  • A check writes nothing. Applying table scripts to the tool's scratch schema no longer leaves empty tables behind in a live database.
  • Seeds run once per database, recorded in deployment_seed_ledger, so a second pass can no longer put shipped defaults back over an operator's values.

The full procedure is in the database deployment guide under docs/guides/.

The application refuses to start without a connection, and names what is missing

A machine with no connection for the records store now stops and names the environment variable that would supply one, instead of going on to read a store that has nothing to open. Store reachability consults what the data seam recorded, so a configured store that does not answer is reported as an outage rather than as an empty read.

No credential is committed any more

The application configuration keeps its shape and the names of the environment variables that supply each value, and holds no credential of any kind. The Infor Visual server, user and password are blank for the same reason: each host supplies its own. This is the one finding in the month with a live blast radius, so it is called out again in Section 6.

Generic requests survive Infor Visual being unreachable

When Infor Visual cannot be reached, the application serves plant reads from a local mirror instead of failing. The generic request's part completions, sequence list, operation state, part quantity and die search used to reach the plant system directly, so with Infor Visual down every one of those steps answered "unavailable" while the work-order flow kept working from the mirror. Four read shapes were added to close that gap, each with its mirror table, staging table, read and refresh procedure, population read and freshness branch, and the generic request now asks the same route as everything else.

A reachable but empty plant result is still treated as a real answer and is never replaced by cached data.

One database engine, at one version

MySQL 5.7 and MAMP were retired across every instruction, ruleset, script and document. The plant host and the local development instance both run MySQL Server 8.0.46, so there is one server version to target and no version split to maintain.

4. Defects fixed

Each row is a fault that was reachable by a person using the application or the tooling.

A layout resource key was read as a property to set on a switch that has no such property, so the page threw while it was being built. The keys were renamed, and a check now fails if any resource key on that page names a property its control does not have.
The generic designation switch saved the moment it was touched, and the preview button was clipped at narrow widths. The switch wrote before the work center was finished, and shared a row with the button. It moved into the Add / Edit form and is written once, after the row is saved.

On a request with no job, the item step's combo box drew nothing and the forward button never opened. The step asked the requesting job's dunnage list, which cannot exist on a request that has no job. The question moved to the step that owns the answer.
The die search errored on the first keystroke. The queue script's early return left the statement before its common table expression unterminated, so the server refused the whole batch. Queue scripts are now audited for that shape.
A freshly installed store had no picture storage settings at all. The image storage overrides were written before a development baseline truncated the settings table. They now run after it and upsert rather than truncate, and the seeded folder is the plant share rather than a retired drive mapping.

Warnings and confirmations looked like a different palette from every other dialog. The message body wrapped itself in a card. It now draws straight on the dialog surface.
Two scrap types raised at one work center were refused as a duplicate. The request's identity ignored the stated type. The stated type is now what the request is about, so the two are two requests.

Typing a part number asked the plant system on every keystroke, and a slow earlier answer could overwrite the right one. Each keystroke started a read. The search now asks once per typing pause and discards a superseded answer by its attempt number rather than by arrival order.
Two Setup review fields showed resource key names instead of words. The keys resolved to nothing. They now resolve, and a test pins them.
A coil weight used the wrong separators and a unit typed into the code. The number is now formatted with the machine's culture and the unit comes from a resource.
Running a deployment check created eight empty tables in the live mirror. The comparer applied table scripts to its scratch schema without re-pointing their database line. It now re-points, and a check writes nothing.

The application could draw the "no image" placeholder as if it were the item's picture. The list and detail page asked only whether a drawable file existed. They now ask the image-path policy, which also refuses the resolver's own "nothing is configured" answer.

One route to the data, and it only runs stored procedures

Five services used to open their own connections. All of them now go through the existing seam, so a change to retry policy, a timeout or how a failed store is reported is made once. The seam refuses anything that is not a stored procedure, which turns a stated rule into an enforced one, and a read past the shared row cap is bounded rather than unbounded. The Infor Visual read path has one implementation instead of two copies that could drift apart.

One idiom, and dependencies that point one way

  • The shared library holds helpers and contracts, not screens; the message dialog body is composed in code and every caller is unchanged.
  • The generic-request libraries no longer reference a waitlist screen project. Raising a request goes through a named interface implemented beside the queue's write door.
  • JSON-backed stores serialize through generated metadata rather than reflection at run time, with one options definition per store.
  • Animations use one library, and the retired toolkit line is gone. The rotating text control uses the same animation idiom and looks the same on screen.
  • The 2,623-line settings view model is now eight cohesive parts behind the same page, with the same bindings and the same messages. It behaves exactly as it did.

The interface does not freeze while it works

Three blocking waits were removed from the settings-load and shutdown paths: the settings view model and the image storage service now await, and the shutdown flush awaits a bounded cancellation instead of waiting on the dispatcher.

The checks that keep it honest

The suite ends the period at 2,915 passed, 66 skipped and 0 failed, with the solution building at zero warnings and zero errors. 17 guardrail tests fail the build when an architecture rule is broken, and this period added new ones: a guard that refuses a temporary preview artefact reachable from the shipped application, an audit that refuses resource keys naming properties their control does not have, an audit that refuses statement text in place of a stored-procedure name, and an audit of the queue scripts' shape. The tests now also prove the strict data route, the row cap, the permanent-error classification, the development-store fallback, and that the two Setup review keys resolve.

Documentation and tooling

  • The four request workflows are mapped as print-ready diagrams — an engineer version and a plain-language version per flow — with 18 refactor findings drawn on the engineer sheets and consolidated into 21 hotspots.
  • UI designs are rendered as a BEFORE and AFTER pair with an approval gate, at three window sizes, composed into a captioned side-by-side comparison.
  • The AI-facing configuration was brought back to the truth: two servers that could not serve were removed, every stated figure corrected, and the documentation lookup tooling declared by the repository so a fresh clone gets it. The always-loaded instruction text shrank by roughly 25,000 tokens of preamble per request with no coding rule lost.
  • A dependency graph extension was built, then moved to its own repository at the end of the period, because an application repository should not build and package a tool that only happens to read it. What remains here is the conventions profile that extension reads.
  • The workflow tooling gained review, specification-test and wireframe extensions, with wireframe sign-off wired so a feature already signed off is never asked twice and a declined mockup never fails a run.
